---
question: 接口自动化里，测试数据的准备和清理你怎么做？
direction: 自动化
difficulty: 中级
tags: [接口测试, 测试数据, 用例隔离]
---

核心目标只有一个：**任何一条用例都能单独跑、重复跑、并发跑，结果一致**。围绕它有几个选择。

**准备方式**，从推荐到不推荐：

1. **用例自造数据**。在用例内部通过业务接口创建自己需要的数据，用完即销毁。最独立，缺点是慢，且依赖创建接口本身可用。
2. **工厂 + 随机化**。用工厂函数生成数据，唯一字段（手机号、订单号、用户名）加随机后缀或时间戳，避免并发时唯一键冲突。
3. **共享基线数据**。预置一批只读的基础数据（如商品类目、权限角色），用例只读不写。
4. **依赖被别的用例创建的数据**。这是反模式，会让用例之间产生隐式顺序依赖，单跑必失败。

**清理方式**：

- 优先用**事务回滚**：如果测试直连数据库且框架支持，每条用例包在事务里，结束时回滚，最干净。但接口测试通常跨进程，事务包不住。
- 其次用**注册式清理**：创建数据时把清理动作压进栈，teardown 时逆序执行。注意清理必须写在 `finally` 语义的钩子里（pytest 的 fixture、JUnit 的 `@AfterEach`），否则断言失败就不清理了，脏数据越积越多。
- 兜底用**定时清扫**：按命名前缀或创建时间批量清理测试数据，防止清理逻辑本身失败导致的泄漏。

**容易被追问的点**：

- **为什么不用固定数据**：固定数据一旦被某条用例改坏，后面所有用例连环失败，且失败原因指向错误的位置。
- **并发怎么办**：唯一字段随机化 + 数据按 worker 分片；不要用「取列表第一条」这种写法，并发下每个 worker 拿到的可能是同一条。
- **清理失败要不要让用例失败**：不要。清理失败应记录告警但不污染用例结果，否则会把一次成功的功能验证误报成失败。
