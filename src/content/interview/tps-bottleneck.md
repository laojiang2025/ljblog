---
question: 压测时 TPS 上不去、响应时间却一直涨，你怎么定位瓶颈？
direction: 性能
difficulty: 高级
tags: [性能测试, 瓶颈定位, 容量规划]
---

先摆结论：TPS 不涨而 RT 变长，说明系统已经到了饱和点，请求在某处排队。定位就是**找出那条队在哪**。

**第一步，先排除压力机自己的问题**。压测端 CPU 打满、线程池不够、网络带宽跑满、连接数受限于本地端口耗尽，都会让你误以为服务端到瓶颈了。看压测机的 CPU、网卡流量，以及施压的实际并发数是否达到了设定值。

**第二步，用 USE 和 RED 两个视角切分**：

- 资源侧（USE）：每个资源看使用率、饱和度、错误数。CPU 使用率、CPU 运行队列长度、内存与 swap、磁盘 IOPS 与 await、网卡带宽。
- 服务侧（RED）：每个服务看请求量、错误率、时延分布。关键是看**分位数而不是平均值**，P99 拉长而 P50 平稳，通常指向 GC、锁竞争或慢查询这类偶发长尾。

**第三步，沿调用链逐段看耗时**。有链路追踪就直接看火焰图或 span 耗时占比，没有就在关键方法埋点。判断依据是：某一段的耗时随并发上升而显著变长，而其他段基本持平，那一段就是瓶颈。

常见的几类瓶颈与特征：

| 瓶颈 | 典型特征 |
|---|---|
| 数据库 | DB CPU 或 IO 高，慢查询数量上升，连接池等待时间变长 |
| 连接池过小 | 应用 CPU 不高，但请求大量卡在获取连接上，队列等待时间接近总耗时 |
| 锁竞争 | CPU 上不去但线程大量 BLOCKED，jstack 多次抓取停在同一处 |
| GC | RT 周期性尖刺，与 Full GC 时间点吻合，吞吐随堆增长下降 |
| 线程池打满 | 拒绝数上升或队列堆积，RT = 排队时间 + 处理时间 |
| 下游服务 | 本服务自身耗时占比低，绝大部分时间花在等待下游响应 |

**第四步，验证而不是猜**。改一个变量、复压一次、对比曲线。只调一个参数才能确认因果，一次改三处调优就说不清是哪个起了作用。

**容易被追问的点**：

- **为什么 TPS 不涨 RT 却涨**：由利特尔法则，并发数 = TPS × RT。TPS 到顶后继续加压，并发数上升只能靠 RT 变长来吸收，多出来的时间全是排队。
- **拐点怎么找**：阶梯加压，观察 TPS 曲线由线性转平的那一点，那才是容量，不要拿压崩前的最大值当容量。
- **优化到什么程度算完**：达到容量目标即可停，继续压下去往往只是在把瓶颈从一个组件搬到另一个组件。
